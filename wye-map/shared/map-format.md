# 맵 쓰는 법 (`.wye/map.json`)

종류·관계 이름은 `SKILL/shared/ontology.md` 표만 쓴다. `check.py`가 이 규칙을 검사한다.

## 모양

```json
{"title": "프로젝트 이름", "brief": "처음 보는 사람에게 들려줄 한두 문장",
 "entities": [{"id": "P1", "type": "Project", "title": "…", "importance": 5,
               "definition": "…", "summary": "…", "whyItMatters": "…", "whatWeKnow": "…", "whatIsMissing": "…", "nextAction": "…",
               "aliases": ["…"], "properties": {"…": "…"}, "evidence": [{"doc": "D003", "quote": "원문 그대로"}]}],
 "relations": [{"fromId": "…", "type": "BLOCKS", "toId": "…", "why": "왜 이었는지 한 문장", "evidence": []}],
 "conflicts": [{"id": "X1", "topic": "…", "entityIds": ["…"], "claims": [{"value": "…", "doc": "D003", "quote": "…"}], "ask": "누구: 무엇을"}]}
```

## 항목
- **실재하는 것**(공정·설비·시스템·제품·조직·화면·지표·현상·결정)과 **자료가 요구하는 것**(요구사항·제약·전제)만 항목이 된다.
  목차·절 제목·표 캡션·인사말은 항목이 아니다. 제목이 가리키는 실체가 있으면 그것을 항목으로("3.2 가동률 정의" 절 → KPI "가동률").
- 같은 대상은 항목 하나, 다른 표기는 `aliases`. 서로 다른 대상을 하나로 뭉치지 않는다.
- `evidence`는 1~3개, 원문 한 문장(20~120자)을 **글자 그대로**. 문서 id(`doc`)만 적으면 `check.py`가 조각 번호를 채운다. 찾지 못한 인용은 오류다.
- `definition`은 "이것이 무엇인가"(프로젝트 사정 없이도 뜻이 서게), `summary`는 "이 프로젝트에서 어떤 상태인가"(두 문장 이내).
- `whyItMatters`는 위치가 아니라 걸린 것 — "이 값이 없으면 표준과 실제를 대조할 수 없다"처럼. "핵심이다"는 쓰지 않는다.
- 나머지 칸(`whatWeKnow`·`whatIsMissing`·`nextAction`)은 한 문장씩, 자료가 말하지 않으면 키를 빼고 빈 값을 쓰지 않는다.
- `importance` 1~5: 5는 프로젝트가 풀려는 문제의 중심, 1은 곁가지. 모두 5로 두지 않는다.
- `properties`는 그 종류에 정해진 키만(ontology.md 표). 수치는 자료에 있을 때만.

## 연결 — 이어지지 않은 항목은 맵에 오르지 못한다
- 프로젝트(Project) 항목을 하나 두고 목표·범위·대상 공정·관계자를 거기에 잇는다.
- 항목마다 "어느 목표·문제·공정에 걸리는가"를 묻는다. 여러 곳에 걸리면 관계를 여러 개.
- 자주 쓰는 자리: 설비 → 그것이 쓰이는 공정 / 시스템 → 받치는 공정·요구사항 / 현재 방식 → 수행 공정(PERFORMED_IN)·만드는 문제(CAUSES)·판단하는 지표(JUDGES) /
  관찰 현상 → 나타나는 곳(OBSERVED_IN)·가리키는 문제(INDICATES)·나쁘게 하는 지표(HURTS) / 필요 데이터 → 쓰는 요구사항(NEEDS)·내주는 시스템(PROVIDED_BY) /
  관계자 → 프로젝트(PARTICIPATES_IN)·맡은 것(OWNS).
- **관계마다 `why` 한 문장.** 못 쓰겠으면 그 관계는 만들지 않는다. 두 항목을 잇는 문장이 원문에 있으면 `evidence`에 하나, 없으면 비운다(화면에 "해석"으로 보임).
- 걸 곳이 정말 없으면 지어내지 않는다 — `check.py`가 "보류"로 알려 주면 위 자리를 다시 찾고, 그래도 없으면 지운다.

## 문제 정의 고리 — 문제마다 찾는 네 자리
1. 현상: `관찰 현상 --INDICATES--> 문제`
2. 지표: `현상(또는 문제) --HURTS--> 지표`
3. 현재 판단: 지금 누가 무엇으로 판단하는가 → `현재 방식 --JUDGES--> 지표·현상`
4. 판단에 쓰는 데이터: `현재 방식 --USES--> 필요 데이터`

자료가 말할 때만 잇는다. 빈 자리는 비워 두면 화면·질문지가 "물을 것"으로 보낸다 — 지어낸 고리는 틀린 문제 정의가 된다.

## 읽는 순서
프로젝트 → 목표와 지표 → 문제와 그 네 자리 → 요구사항·필요 데이터·시스템 → 결정·제약·관계자 → 문서끼리 어긋난 값(`conflicts`).
